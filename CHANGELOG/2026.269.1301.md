# 2026.269.1301 — fix(scaffold): correct the scaffold the main bootstrap seeded from the template

## Summary of changes

Corrects the repo scaffold that the `main` bootstrap seeded into this new repo, and repairs
the Go gate it broke. The bootstrap (`opencharly/.github` `bootstrap-repo-main.yml` →
`scripts/bootstrap-repo-main.sh`) creates the first protected `main` **from the already-pushed
`feat/cua` head**, so `main` began carrying the feature-branch content verbatim, including
scaffold defects copied from the `plugin-jetkvm` template.

The concrete edits:
- **`.github/workflows/ci.yml`** — REPAIRED. It was copied from `plugin-jetkvm` and its
  `go-version-file` / `cache-dependency-path` / `working-directory` pointed at
  `candy/plugin-jetkvm/…`, a path that does not exist here, so every gate step would fail.
  Repointed to `candy/plugin-cua/…` and the JetKVM prose replaced with this repo's real
  rationale.
- **`candy/plugin-cua/client.go`** — removed `hostname()`, an unused helper (its only
  reference was its own definition).
- **`candy/plugin-cua/kind.go`** — removed `kindCapability()`, an unused helper that was a
  redundant **duplicate** (R3) of the inline `{Class: "kind", Word: "cua", InputDef:
  "#CuaDeviceInput"}` capability already advertised in `plugin.go:46`.
- **`deploy.yml`** — pin `v2026.258.0219` → `v2026.269.1034`.
- **`.gitignore`** — extended with the canonical charly-generated-artifact patterns.

The plugin's substantive content (the `cua` verb, the `kind: cua` entity, the CUE schema,
the client/catalog/providers, 8 Go tests, and the `cua-verb-probe` bed) is already on `main`
via the bootstrap seed.

### Why the gate was repaired, not deleted

An earlier revision of this PR deleted `ci.yml`; that was wrong, and the review caught it.
The reasoning error was answering *"is a repo-local check **required** org-wide?"* (no — the
org ruleset requires exactly one check, `validate / validate`) and drawing a conclusion about
a different question: *"does it **run this repo's tests**?"* (yes). A test gate's purpose is
to run THIS repo's tests, and this repo ships a real Go module with 8 unit tests that nothing
else runs — `deploy.yml` checks only the manifest and the bed only exercises verb dispatch.
So the correct action is to repair the gate. (`layer-cua`, the companion repo, ships **no** Go
module, so its `ci.yml` gates nothing and is correctly deleted there — same review round, the
opposite disposition, decided by whether the repo has Go code to gate.)

### The repaired gate immediately caught two real defects

Running the repaired gate surfaced exactly the class of defect it exists to catch — dead code
(R5), previously invisible because nothing ran `golangci-lint`:

```
$ golangci-lint run ./...
client.go:116:6: func hostname is unused (unused)
kind.go:111:6: func kindCapability is unused (unused)
2 issues: * unused: 2
```

Both are removed above (`kindCapability` was also a duplicate of the inline capability — R3).
